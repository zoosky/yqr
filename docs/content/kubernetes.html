yqr · Kubernetes

Chart a path to any field in a manifest.

yqr is a jq-style filter for YAML. Point it at a manifest file, a kubectl get -o yaml dump, or a Helm-rendered bundle, and it walks straight to the field you asked for — as a value, not as JSON you have to decode back.

the filter .spec.volumes[0].secret.defaultMode 
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  volumes:
    - name: tls
      secret:
        secretName: web-tls
        defaultMode: 0640
default pipeline 
$ yqr '.spec.volumes[0].secret.defaultMode' pod.yaml
640
--engine rust-yaml 
$ yqr --engine rust-yaml '.spec.volumes[0].secret.defaultMode' pod.yaml
0640

Kubernetes spells file permissions in octal — defaultMode: 0640 on a Secret or ConfigMap volume. Read that field through yqr's default, re-serializing pipeline and the leading zero is gone: 640 is a different number. Select a fidelity engine and the value comes back exactly as written, because yqr never re-typed it in the first place.

installed paths

Where the binary actually lives

yqr isn't packaged anywhere yet — every path below comes from building the crate yourself.

On your machine

cargo build --release

Binary lands at target/release/yqr.

cargo install --path .

Installs to ~/.cargo/bin/yqr — keep that directory on PATH so plain yqr resolves from any shell, including one already piping kubectl output.

Inside a container image

/usr/local/bin/yqr

Build it in a multi-stage Dockerfile and copy just the binary into the runtime stage — no Rust toolchain, no source tree, in the image that actually ships.

Byte-preserving reads are opt-in at build time. A plain cargo build --release binary has no --engine flag — it exists to keep the default build dependency-minimal. Ask for it and you get told exactly how to get it: 
$ yqr --engine rust-yaml '.' pod.yaml
yqr: io error: engine 'rust-yaml' is not available in this build (rebuild with: cargo build --features backend-rust-yaml)
Rebuild with the feature enabled and the flag works: 
$ cargo build --release --features backend-rust-yaml
(backend-noyalib is the other available engine.) If you're baking yqr into a container image specifically to query manifests byte-exactly, turn the feature on in the build stage.

two ways to run it against a cluster

From an operator's shell, or from inside the image

Piped from kubectl

Standard operator loop: dump a resource as YAML, pull one field out of it, move on.

$ kubectl get pods -o yaml | yqr -r '.items[] | .metadata.name'

One pod name per line.

$ kubectl get pod web-0 -o yaml | yqr -r '.spec.containers[0].image'

The primary container's image, unquoted.

$ kubectl get pod web-0 -o yaml | yqr -r '.spec.initContainers[]? | .image'

Init container images when the pod has any — the trailing ? keeps pods with none from erroring the pipeline.

Inside a container image

Bake the binary in, then use it in an init container to read a mounted manifest or ConfigMap before the main container starts.

# -- build --
FROM rust:1.96-slim AS build
WORKDIR /src
COPY . .
RUN cargo build --release --features backend-rust-yaml

# -- runtime --
FROM debian:bookworm-slim
COPY --from=build /src/target/release/yqr /usr/local/bin/yqr
ENTRYPOINT ["yqr"]
$ yqr -r '.data.enableBeta' /config/values.yaml

Read a flag out of a mounted ConfigMap and hand it to the next step — a common init-container job.

beyond the cluster

It's not just Kubernetes

Anything that's YAML takes the same filters. Three more places yqr earns its keep.

CI/CD pipelines

GitHub Actions workflows are YAML. Audit what a job actually runs without opening the file — these two ran against this repo's own ci.yml.

$ yqr -r '.jobs.test.["runs-on"]' ci.yml

ubuntu-latest — bracket syntax reaches keys a bareword can't spell, like runs-on.

$ yqr -r '.jobs.test.steps[1].with.toolchain' ci.yml

1.96 — confirm the pinned Rust version without scrolling past the cache step.

Docker Compose

Check what a compose file is about to pull and expose before you run it.

$ yqr -r '.services[] | .image' compose.yaml

yqr-demo:latest, postgres:16 — every image referenced, one per line.

$ yqr -r '.services.web.environment.LOG_LEVEL' compose.yaml

debug — one config value, no grep.

Ansible playbooks

A playbook is a YAML list of plays — walk it like any other sequence.

$ yqr -r '.[0].tasks[] | .name' playbook.yml

Install nginx, Start nginx — every task in the first play, at a glance.

$ yqr -r '.[0].hosts' playbook.yml

web — which hosts that play targets.

filter grammar

What yqr can walk today

yqr is at milestone M0. This is the whole grammar — every recipe on this page is built from it.

FilterMeaning
.Identity
.fooField access
.a.bNested field access
.[n]Array index (.[-1] counts from the end)
.[]Iterate sequence elements / mapping values
a | bPipe
f?Suppress runtime errors from f (e.g. iterating a field that turns out to be missing or the wrong shape)

Not yet available: select(), map(), keys, arithmetic, and object/array construction. Reach for kubectl's own -o jsonpath or a grep in the meantime if a recipe needs one of those.
